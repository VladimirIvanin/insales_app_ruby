# InSales Partner App — Ruby

Заготовка устанавливаемого партнёрского приложения InSales на Rails и SQLite.
Законченный сценарий: установка, вход сотрудника через token3, проверка API,
повторный вход после перезапуска и удаление подключения.

Ruby 4.0.8, Rails 8.1.4, SQLite3 gem 2.10.1, Puma 8.0.2, RSpec Rails 8.0.4.
Ruby выбран по доступному официальному образу `ruby:4.0.8-slim-trixie`.
Точные версии зависимостей находятся в `Gemfile.lock`.

## Быстрый старт с Docker

Нужны Docker Engine и Docker Compose 2.24+.

```sh
cp .env.example .env
openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32
```

Запишите три разных результата в `SECRET_KEY_BASE`,
`AR_ENCRYPTION_PRIMARY_KEY` и `AR_ENCRYPTION_KEY_DERIVATION_SALT`.
Заполните остальные обязательные настройки:

| Переменная | Назначение |
|---|---|
| `INSALES_APP_ID` | API-идентификатор приложения из кабинета разработчика |
| `INSALES_APP_SECRET` | Секрет приложения |
| `APP_BASE_URL` | Публичный HTTPS origin приложения, например `https://app.example.com` |
| `ALLOWED_SHOPS` | Разрешённые домены магазинов через запятую, с точным совпадением |
| `SECRET_KEY_BASE` | Постоянный независимый секрет для шифрования Rails-cookie |
| `AR_ENCRYPTION_PRIMARY_KEY` | Постоянный независимый ключ шифрования паролей в БД |
| `AR_ENCRYPTION_KEY_DERIVATION_SALT` | Независимая соль выведения ключа шифрования |

Сохраните ключи: новый запуск не должен создавать новые значения. Смена
`SECRET_KEY_BASE` прекращает старые браузерные сессии. Потеря ключа или соли
шифрования делает сохранённые API-пароли нечитаемыми. Ключи храните отдельно от
резервной копии SQLite и не включайте в образ или Git.

```sh
docker compose build
docker compose run --rm app bin/rails db:prepare
docker compose up -d
curl http://127.0.0.1:8765/healthz
```

SQLite хранится в именованном volume `app_data` и сохраняется при пересоздании
контейнера. `docker compose down -v` удаляет этот volume вместе с данными.
Образ запускает один Puma-процесс с тремя потоками. После изменения исходников
выполните `docker compose up -d --build`.
При запуске сервера entrypoint автоматически выполняет `db:prepare`, включая
новые миграции. Перед обновлением сохраняйте согласованный backup SQLite и ключи.
Миграция постоянного ID переносит существующие credentials и pending; её откат
требует восстановления backup. Compose проверяет `/healthz` каждые 30 секунд.

Для callback'ов нужен доступный InSales HTTPS-адрес: сервер или туннель на порт
8765 с завершением TLS и корректной передачей схемы HTTPS. `.env.example` задаёт
`RAILS_ENV=production`; оставьте этот режим для подключения к InSales, включая
публичный туннель. `APP_BASE_URL` должен совпадать с публичным адресом.
Приложение открывается в новой вкладке; встраивание в iframe не поддерживается.
Локальный `http://127.0.0.1:8765` допустим с `RAILS_ENV=development` для проверки
запуска без внешнего доступа. Этот режим не предназначен для публичного размещения.

## Настройка приложения в InSales

Создайте партнёрское приложение и укажите:

| Настройка | URL |
|---|---|
| Установка | `https://app.example.com/install` |
| Вход | `https://app.example.com/login` |
| Удаление | `https://app.example.com/uninstall` |

Адрес возврата после подтверждения входа приложение формирует само:
`APP_BASE_URL/auth/callback`. Для проверки подключения нужно чтение аккаунта;
примеры orders/products требуют соответствующих прав приложения.

Домен магазина добавляется в `ALLOWED_SHOPS` без схемы, порта и пути. Регистр
не учитывается. Поддомены автоматически не разрешаются.
Эта политика рассчитана на приватное приложение. Для публичного приложения нужна
отдельная политика разрешённых доменов с проверкой связи домена и `insales_id`;
не заменяйте её безусловным разрешением любого hostname из callback.

## Запуск без Docker

Установите Ruby 4.0.8 через менеджер версий. Для сборки native gems могут
понадобиться компилятор, заголовки SQLite и libyaml.

```sh
gem install bundler -v 4.0.23
bundle install
cp .env.example .env
# Заполните .env и создайте три независимых секрета, как описано выше.
bin/rails db:prepare
bin/rails server -b 127.0.0.1 -p 8765
```

Уже экспортированные переменные важнее `.env`. По умолчанию локальная development
БД находится в `storage/development.sqlite3`; `APP_DB` переопределяет путь.
Для локальной development-проверки задайте `RAILS_ENV=development` и
`APP_BASE_URL=http://127.0.0.1:8765`. Для внешних callback используйте production.

## Маршруты и диагностика

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/healthz` | Доступность Rails-процесса |
| GET | `/install` | Приём установки |
| GET | `/login` | Начало входа |
| GET | `/auth/callback` | Подтверждение token3 |
| GET | `/` | Страница подключения, нужна сессия |
| POST | `/probe` | Чтение `account.json`, нужна сессия и CSRF |
| GET | `/account` | Однократный результат после POST `/probe`, нужна сессия |
| POST | `/logout` | Завершение входа, нужен CSRF |
| GET | `/uninstall` | Удаление подключения |

```sh
docker compose run --rm app bin/rails db:migrate:status
docker compose run --rm app bin/rails insales:doctor
docker compose run --rm app bin/rails insales:cleanup
```

`doctor` проверяет конфигурацию, миграции и API активных магазинов. Он не активирует
кандидатов и завершает работу с ненулевым кодом при ошибке. Без Docker используйте
те же команды, убрав `docker compose run --rm app`.
Кнопка API использует POST → redirect → GET. Обновление страницы результата
возвращает на главную без повторного API-запроса; для новой проверки нажмите кнопку.
Если магазин исключён из `ALLOWED_SHOPS`, doctor сообщает `not allowed`, проверяет
остальные магазины и возвращает ненулевой код. Следующее обращение со старой
сессией такого магазина отзывает все его сессии и challenges.

`cleanup` удаляет просроченные pending/challenges/сессии, истёкшие разрешения
проверки и revocations старше 30 дней. Запускайте её регулярно своим планировщиком.
После удаления старой revocation повтор uninstall может вернуть `403`, а повтор
старого install снова попадёт в pending и потребует настоящей проверки API.

## Регулярная очистка и резервные копии

Например, запускайте `insales:cleanup` раз в сутки из системного cron владельца
Compose-проекта. Замените `/srv/insales-app` своим каталогом; журнал ограничивайте
штатной ротацией логов:

```cron
17 3 * * * cd /srv/insales-app && /usr/bin/docker compose run --rm --no-deps -T app bin/rails insales:cleanup >> /srv/insales-app/log/cleanup.log 2>&1
```

Для простого согласованного backup остановите приложение и все внешние процессы,
которые пишут в его БД, включая cleanup. Пока они остановлены, сохраните весь
volume SQLite, включая возможные WAL/SHM-файлы. Не копируйте только основной
SQLite-файл работающего приложения.

```sh
backup_dir="$PWD/backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
chmod 700 "$PWD/backups" "$backup_dir"
docker compose stop app
docker compose run --rm --no-deps --user root -T -v "$backup_dir:/backup" app \
  tar -C /app/storage -czf /backup/app-data.tar.gz .
docker compose up -d app
```

Архив содержит credentials в зашифрованном виде и данные сессий; храните его с
ограниченным доступом. Отдельно сохраните постоянные ключи, настройки `.env` и
версию образа/исходников. Периодически проверяйте восстановление в изолированной
среде с этими ключами.

Для восстановления выберите каталог backup и соответствующую версию образа.
Остановите всех писателей БД, сохраните текущий volume перед заменой, затем:

```sh
backup_dir="$PWD/backups/REPLACE_WITH_BACKUP_DIRECTORY"
docker compose stop app
docker compose run --rm --no-deps --user root -T -v "$backup_dir:/backup:ro" app \
  sh -eu -c 'tar -tzf /backup/app-data.tar.gz > /dev/null; find /app/storage -mindepth 1 -maxdepth 1 -exec rm -rf {} +; tar -C /app/storage -xzf /backup/app-data.tar.gz; chown -R app:app /app/storage'
docker compose up -d app
docker compose exec -T app bin/rails insales:doctor
```

Перед удалением текущих данных проверьте архив (`tar -tzf`) и путь к нему.
Возвращайте совместно данные, ключи и соответствующую версию приложения. Старый
код с новой схемой одновременно не запускается; необратимая миграция откатывается
восстановлением backup, а не `db:rollback`.

## Жизненный цикл

`GET /install` сохраняет непроверенного кандидата с паролем
`MD5(install_token + app_secret)` и обычно отвечает `200` без API-запроса.
Получение callback само по себе не подтверждает владельца магазина и не выдаёт
сессию. Повтор тех же credentials идемпотентен. На домен допускаются пять
кандидатов сроком семь дней. Просроченные кандидаты очищаются при следующем install.
Повтор не продлевает TTL. Магазин определяется постоянным `insales_id`, а домен
хранится в кандидате до проверки `account.id`. Проверенная смена домена обновляет
существующее подключение и отзывает старые сессии. Если домен перешёл другому
магазину, его прежнее подключение отключается только после такой проверки.

При заполненной очереди install проверяет занявших её кандидатов, начиная со
старейшего, независимо от заявленного ими ID. Проверка выполняется вне
write-транзакции: максимум пять запросов `account.json` с общим сетевым бюджетом
три секунды. Первый кандидат с ответом `401`/`403` или несовпадающим `account.id`
удаляется в одной транзакции с сохранением новой установки. Успешно проверенный
кандидат сохраняется без активации. Таким образом, пять поддельных pending не
блокируют настоящую установку на весь срок хранения, а возраст записи сам по
себе не позволяет её вытеснить.

Сеть, `429`, `5xx`, неожиданный HTTP-статус или некорректный ответ прекращают
очистку без удаления кандидата. Если место освободить не удалось, install
возвращает `503`; после восстановления API повторите установку из InSales.
Удалять SQLite или ждать семидневного TTL для восстановления не требуется.
При одновременных install место может занять другой запрос; неуспешный callback
также требует повтора. Действующие credentials и сессии очистка не меняет.

Первый `GET /login` проверяет самого нового подходящего кандидата одним запросом
`account.json` с общим пределом пять секунд и сверяет `account.id`.
Ответ `401`/`403` или чужой ID отклоняют кандидата. Сеть, `429`, `5xx`, другие
HTTP-ошибки и некорректный ответ сохраняют его для повторного входа. При неудаче нового
кандидата действующее подключение продолжает работать. Если действующего
подключения ещё нет, временный отказ возвращает `503` с предложением повторить
вход; отсутствие установки или неверные credentials возвращают `401`.
Фоновой проверки нет. Если первый вход выполнен позже семи дней после install,
кандидат уже недействителен: вход вернёт `401`, даже если приложение ещё видно
в InSales. Удалите приложение в InSales, установите заново и откройте его в течение
семи дней. Для уже активированного подключения TTL кандидата не ограничивает вход.

Публичные install/login ограничены 60 запросами в минуту на IP и 30 на домен
для одного процесса; превышение возвращает `429` и `Retry-After: 60`.
Дополнительно SQLite хранит общий для всех кандидатов домена бюджет: 10 API-проверок
за минутное окно. Один кандидат проверяется не чаще раза в 10 секунд; успешный
результат переиспользуется в этот короткий период. Перезапуск не сбрасывает
бюджет API. Одновременно допускаются две проверки; остальные быстро возвращают
`503`, оставляя поток для install и других запросов. Аварийные разрешения на
проверку истекают через шесть секунд. `Retry-After` откладывает дальнейшие
проверки домена и сохраняется в SQLite.

Каждая проверка расходует общий API-лимит приложения в магазине, включая запросы
с неверным паролем. Собственные операции API используют оставшуюся квоту.
Лимит callbacks по IP хранится в памяти и сбрасывается после рестарта; на внешнем
proxy также нужны подходящие ограничения. Следующий шаг при росте нагрузки —
фоновая проверка с постоянной очередью вместо ожидания API в веб-потоке.

Затем браузер получает одноразовый challenge на пять минут и переходит в InSales.
`GET /auth/callback` проверяет token3, браузер и поколение подключения. Только
после этого создаётся сессия. Каждый вход получает отдельный `flow` и браузерную
cookie, поэтому второй начатый вход не затирает первый. Challenge потребляется
атомарно; повторный callback не создаёт вторую сессию. При повторном входе без нового кандидата API-проверки нет.

Сотрудник может входить по телефону без email. Callback принимает `user_email=`
и `user_email` без значения: для token3 оба варианта дают пустую строку.
Сам параметр email обязателен. Имя `user_name` может отсутствовать, быть пустым
или передаваться без значения; для подписи это пустая строка. Массивы, объекты
и строки email/имени длиннее 1024 байт отклоняются.

Token3 подписывает конкатенацию полей без разделителей. Например, `name=N,id=42`
и `name=N4,id=2` дают одинаковые подписанные байты. Поэтому подпись подтверждает
вход в контекст магазина по challenge, но не удостоверяет каждое поле сотрудника
отдельно. `AppSession#callback_user_id` и подпись «ID сотрудника из callback» в UI —
метаданные callback; существующая колонка `user_id` сохраняется для совместимости.
Не используйте этот ID как единственное основание персональных прав или строгого
аудита действий сотрудника. Для этого нужна независимая аутентификация личности;
проверки существования ID в магазине недостаточно. Одностороннее изменение хеша
или добавление разделителей нарушит совместимость с InSales.

`GET /uninstall` принимает готовый пароль подключения, без повторного MD5.
В одной транзакции отменяются только совпавшие credentials и связанные с ними
сессии/challenges. Pending с другими паролями сохраняются. Повтор удаления
подтверждается по минимальной отметке с SHA-256 пароля; рабочий пароль в ней
не хранится. Старый uninstall не удаляет новое поколение подключения.

Страницы и формы передают ожидаемый `store_id`: если другая вкладка переключила
магазин, запрос старой вкладки получает `409`. Параметр проверяет контекст
сессии и не выбирает магазин для авторизации.

## Сессии, шифрование и формы

- Rails CookieStore шифрует браузерное состояние. В cookie нет API-паролей.
- Авторизация дополнительно проверяется по `AppSession` в SQLite. В БД хранится
  SHA-256 случайного токена сессии. Сервер определяет магазин, ID сотрудника хранится
  только как метаданные callback с описанными выше ограничениями token3.
- После token3 вызывается `reset_session`; logout и переустановка отзывают старый
  вход. Сессия действует максимум час, бездействие ограничено 30 минутами.
- Один профиль браузера работает с одним магазином. Вход в другой магазин
  переключает все вкладки. У параллельных входов независимые flow/challenges;
  каждый успешный callback переключает текущую сессию браузера и отзывает предыдущую.
  Для параллельной работы с магазинами используйте разные профили браузера.
- Cookie использует `HttpOnly`, `SameSite=Lax`, `Path=/`, без `Domain`.
  При HTTPS добавляются `Secure` и префикс `__Host-`.
- API-пароли кандидатов и активных подключений шифруются штатным
  Active Record Encryption, AES-256-GCM с недетерминированным шифрованием.
- `/probe` и `/logout` принимают POST с обычной CSRF-защитой Rails и проверкой
  Origin. GET-callback'и InSales проверяются средствами протокола.
- Формы используют `Referrer-Policy: same-origin`; на callback'ах установлен
  `no-referrer`, чтобы query авторизации не передавался в Referer.
- Данные API экранируются ERB; страницы не кешируются. Токены и персональные поля
  callback фильтруются в Rails-логах. Reverse proxy также должен исключать query
  callback'ов из access logs: Rails не управляет его журналом.

В production задайте `RAILS_ENV=production` и завершайте TLS на доверенном reverse
proxy. Он должен передавать правильную схему HTTPS и перезаписывать клиентские
forwarded-заголовки. Production включает принудительный HTTPS; проверьте цепочку
редиректов и cookie через публичный адрес.
`/healthz` доступен по HTTP и IP без forwarded-заголовков; это исключение
относится только к проверке процесса, остальные маршруты сохраняют защиту host/HTTPS.

## API-клиент и расширение

Клиент обслуживает одно подтверждённое подключение. В обработчике сначала
получите магазин из проверенной сессии, затем создайте клиент:

```ruby
client = Insales::Client.new(shop: store.domain, password: store.api_password)
response = client.account
response.data          # Полный JSON Hash без потери полей
response.status        # HTTP-статус
response.usage_limit   # API-Usage-Limit этого ответа

client.list_orders(page: 1, per_page: 50)
client.get_order(123)
client.count_orders
client.update_order(123, { "custom_status" => "accepted" })
client.list_products(page: 1, per_page: 50)
client.get_product(456)
client.count_products
client.update_product(456, { "title" => "Новое название" })
```

Все методы возвращают `Insales::Client::Response`. Для count значение находится
в `response.data["count"]`; успешное обновление с пустым `204` возвращает `data: nil`.
Примеры обновления меняют данные: выполняйте их только на своих тестовых объектах.

Ошибки разделены на `Insales::ApiError` (`status`, `headers`),
`Insales::TransportError` и `Insales::ResourceError`; общий предок — `Insales::Error`.
Клиент проверяет TLS, не следует редиректам, не повторяет запросы автоматически
и ограничивает ответ двумя MiB и общим временем пять секунд.
`ApiError.body` содержит до 64 KiB ответа ошибки, `data` — разобранный JSON либо
`nil`, `usage_limit` и `retry_after` — соответствующие API-заголовки.
Сообщение исключения содержит только HTTP-статус. Тело ошибки может содержать
данные магазина: используйте его для обработки, не записывая целиком в журналы.

Для нового ресурса добавьте явный метод в `Insales::Client`: подтверждённые метод,
путь, query, JSON root и проверку формы ответа. Повторно используйте приватный
`request`; не передавайте ему произвольные URL из пользовательских параметров.
Контракт нового метода проверьте настоящим HTTP против симулятора.

## Проверки

Автономный набор не требует `.env`, credentials или исходников InSales:

```sh
docker compose build checks
docker compose run --rm checks
```

Сервис `checks` собирает Docker target `test`: в нём есть Git для обновления
базы advisories. Обычный образ `app` не содержит Git и его дополнительных
зависимостей. Для `bin/check` без Docker нужен установленный Git.
JSON устанавливается из `Gemfile.lock` и доступен также обычному Ruby без Bundler.
В рабочем образе старые Ruby-файлы и native extensions удаляются вместе с default gem.

`bin/check` выполняет RSpec, Zeitwerk, RuboCop, Brakeman и аудит зависимостей.
`bin/check` сохраняет RSpec seed и результаты в `tmp/check/rspec.json`.
Последний шаг использует сеть для обновления базы уязвимостей. Отдельно тесты:

```sh
docker compose run --rm checks bundle exec rspec
```

Каждый запуск RSpec создаёт собственную временную SQLite. Симулятор обслуживает
настоящие HTTP-запросы клиента и цепочку token3, отклоняет неизвестные пути и
неверную авторизацию. HTTP разрешён клиенту только для loopback-симулятора в
`RAILS_ENV=test`; production-переключателя ослабления TLS нет.

Проверка финального образа через штатный production entrypoint:

```sh
docker build -t insales-app-ruby .
bin/check-image insales-app-ruby
```

Она использует синтетические настройки и временный volume, проверяет миграции,
HTTP health, host/HTTPS policy, сохранение pending credentials после restart и
отсутствие `.agents`, `.codex`, `.cursor` в образе. Нужны Bash, curl и OpenSSL;
внешний InSales и его credentials не используются. HTTPS-заголовок в smoke
имитирует доверенный proxy; проверка не подтверждает TLS handshake.

CI запускается на push/PR, вручную и раз в неделю. Тесты/статический анализ,
`bundler-audit check --update` и сканирование финального образа Trivy выполняются
независимыми jobs. Trivy проверяет OS/library packages и отклоняет HIGH/CRITICAL,
включая ещё не исправленные уязвимости; исключения по умолчанию не заданы.
Рабочий образ использует официальный Ruby runtime; gems копируются из build stage.
Сканирование пакетов не доказывает отсутствие всех уязвимостей Ruby/native binaries.
Seed, журналы ошибок и JSON-отчёт Trivy сохраняются
на 14 дней. Список найденных CVE также выводится в лог image-audit.
Наличие HIGH/CRITICAL без выпущенного исправления оставляет job красным;
обновление сканера само по себе эти пакеты не исправляет. Сборка тестов специально
добавляет локальные markers в контекст,
чтобы проверка исключений работала и в чистом checkout.
Dependabot настроен для bundler, Docker и GitHub Actions. Alerts/security updates
требуют настройки самого GitHub-репозитория; наличие workflow их не включает.

Отдельная проверка совместимости на своём тестовом магазине:

1. Установить приложение и открыть его из InSales.
2. Проверить магазин и отображение ID из callback с учётом ограничения token3;
   совпадение этого ID не доказывает личность сотрудника.
3. Нажать «Проверить API» и получить account магазина.
4. Перезапустить контейнер; проверить текущую сессию и новый вход из InSales.
5. Выйти; убедиться, что прежняя сессия больше не открывает страницу.
6. Удалить приложение из InSales и проверить прекращение доступа.
7. Повторно установить и открыть приложение.

Успех симулятора не подтверждает совместимость с настоящей платформой или
поведение cookie в браузере: такой прогон выполняется отдельно.

## Ограничения

Один экземпляр приложения и SQLite на локальном диске. Есть несколько магазинов,
но нет фоновых задач, вебхуков, платежей и OAuth/OIDC покупателей. При временной
ошибке первой проверки пользователь повторяет вход. Для резервного копирования
используйте согласованный SQLite backup вместе с отдельным сохранением ключей.
Поколение подключения — ID подтверждённого кандидата. Постоянный счётчик
`InstallationSequence` выдаёт эти ID в одной транзакции с установкой и сохраняется
после очистки pending и uninstall. Миграция учитывает уже выданные ID и поколения.
Записи используют `BEGIN IMMEDIATE` SQLite,
условное потребление challenge и блокировки магазинов. Переход на другой адаптер
требует пересмотра конкурентного admission и повторных конкурентных тестов.
Сессия обновляет время активности не чаще раза в минуту.
